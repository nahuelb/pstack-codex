# Codex delivery flow

Apply this extension during existing framing, implementation and final handoff for multi-part work. It adds no separate phase or authority.

## Prove the decisive boundary early

Identify the first usable path within the full accepted scope and the assumption most likely to invalidate its design. Choose the real execution surface that can disprove that assumption. Run the smallest decisive experiment before expanding dependent foundations.

A native storage test does not prove cold-start bridge or notification behavior. A public component pass does not prove its consumer's authentication and transaction behavior. State simulated boundaries explicitly. If access is missing, surface it early and continue independent work; do not substitute a weaker experiment and mark the original criterion passed.

Use the existing acceptance checks to cover relevant failure transitions, such as stale consent, replay, concurrent mutation, ownership transfer or shared event identity. Select cases from the actual contract, not a mandatory checklist for every task.

When a discovered requirement replaces a foundation or adds a major prerequisite, update the remaining dependency path before expanding it. The first usable path is a milestone, not permission to omit platforms, reviews or delivery requirements.

## Prepare execution before repeated proof

Before dispatching browser verification, establish the intended build, isolated runtime, ready URL, fixture access, expected flows and artifact destination. Delegate browser controls under the applicable browser policy; the runtime owner prepares and cleans its own services. A missing runtime is a setup dependency, not a browser failure.

Use the project's preflight to check the actual checkout, toolchain, package versions, installed resolution and CI networking before broad verification or consumer import. When building or extending a verifier, read [verified execution](codex-verified-execution.md) for source capture, execution binding and observed milestones. Keep independent source and build ownership separate. Start task-owned emulators when their tests are ready; record readiness separately from background lifetime and stop them after the owning tests finish.

Reuse unaffected source-bound proof during correction, and rerun affected flows after relevant changes. Preserve required final integrated verification. Follow the existing browser recovery rule for failed controls; if recovery cannot establish the required observation, report the missing capability instead of repeatedly attempting the same unsupported path.

## Collect PR feedback without stopping the build

Opening or updating a PR need not stop independent implementation. Before final handoff, read the current head, review threads and CI. Triage available findings through the existing Babysit policy. Fix confirmed in-scope defects and verify the changed revision before claiming review completion.

For explicitly authorized automatic-review follow-through, keep review collection assigned to the main agent until the requested review completes or a concrete blocker is reported. Continue useful independent work while it runs. If the review is still pending at handoff, state that clearly; a passing CI run does not establish review completion.

Check the current head again before acting on a review result. Stale comments still need disposition, but an older clean review cannot approve a new head. When PR check rollups are missing, inspect exact-head workflow runs and report the distinction.

Use the existing review triage to batch coherent fixes. Reply or resolve threads only within messaging authority. Do not infer merge, deployment or recurring-monitor permission from a request to implement or push. Report implementation verified, review handled, merge-ready, merged and deployed as separate observed states.
