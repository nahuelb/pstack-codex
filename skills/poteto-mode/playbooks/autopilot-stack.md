### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack she reviews and lands herself.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it". The sibling of **Autopilot-full**. The owner loop and verification gate are the same. A clean verdict appends one link to the reviewed chain, and nothing auto-ships.

1. **Run the owner loop unchanged.** One isolated Codex worktree agent per PR owns build, its first push, a ready GitHub PR, self-proof, skeptical Bugbot triage, `$unslop`, `$no-comments`, and babysit to green. Owners parallelize only with proven isolation. Within about 15 minutes, every owner starts an uncommitted `decisions.tsv`, pushes its first branch snapshot, and opens the PR ready. Every owner returns that trail.
2. **Audit on the wake chain.** The operator's explicit go authorizes a thread heartbeat around every 30 minutes. Never hold a shell open to sleep. At each tick, re-read this playbook from trunk and inspect the live goal. Probe owners through supported live status and judge progress by commits, pushes, pull-request or check deltas, and store reports. Cancel or stand down a stuck lane, reconcile partial state, and make at most one bounded replacement.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On her explicit go, create a goal with the full program objective. The goal continues across turns until the chain is done. On her stop, every owner takes an immediate zero-writes hold.
4. **Verify at STACK-READY.** The owner reports STACK-READY with the exact head SHA. The main agent swarm-verifies that SHA per the **swarm** skill. The lanes rerun the gates, prove the load-bearing behavior live, and audit the receipts and diff. One regression lane runs the same scenario on trunk and head. If trunk lacks the feature, it records that fact and gates the added behavior plus the end state the user expects. Findings return to the owner, and nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to one linear base-branch stack in verified order or an order the operator specified.
6. **Keep one topology writer.** Owners push only their own branches and report each tip, current base, and intended parent. The main agent is the only topology writer. To append a PR, fetch the intended parent, rebase the child onto that exact tip, check `ls-remote`, push with `--force-with-lease`, and set the PR base to the parent branch with `gh pr create --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk.
7. **Absorb drift at the root, then re-verify what moved.** Fetch current trunk and rebase the chain from bottom to top. An owner fixes conflicts in its own files, and the main agent pushes the result. A rebase rewrites the SHAs above it and voids old verdicts. Compare each verdict's stable base-to-head `git patch-id` with the new base-to-head patch. An unchanged patch keeps the code verdict, but mergeability and CI must run again. Any changed patch returns to step 4. The countersign rule remains unchanged from Autopilot-full.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up on GitHub. Every link carries its verifier verdict in the PR body or a comment. The operator reviews and lands it with her own clicks or merge-when-ready action.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
